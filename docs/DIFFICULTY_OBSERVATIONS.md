# Generated difficulty observations — first web slice

This is **measurement infrastructure, not automatic balancing or proof of a better game**. The web client's free hints and the server's paid reward rules are unchanged. All observations are best-effort and separate from payouts, competitive rankings, and `POST /api/level-results` (the older, client-authored legacy-level tuning pool). Neither a solver witness nor 20 attempts measures enjoyment, human fairness, or accessibility.

## What is measured

For authenticated **v4/v5 classic and daily** generated boards only, the server writes one `started` row after saving each energy spend, and at most one terminal row after saving a completed, closed, replaced or expired attempt. `verified_win` requires the already-existing pinned board/replay validation. `unverified_win` is deliberately separate (e.g. old clients without a replay). Loss and quit are **client reports**, not replay-proven outcomes; `replaced` is a new spend superseding an unfinished attempt; `expired` is detected when an old attempt is superseded. None of these categories can trigger rewards or change a target.

The web client sends a reported hint count with wins, reports a loss when the ordinary level ends without a win, and can send an explicit `quit` through `POST /api/account-economy/attempt/close` when a UI explicitly abandons an attempt. Opening the DOM menu **pauses** play; it is not a quit. A replaced attempt without a close has an unknown quit point. The authenticated close endpoint consumes only its matching outstanding attempt; repeated/late completion and closing cannot pay. The server counts actual attempt-bound booster receipts for verified-win assistance, but free hint counts and loss/quit progress are client-reported. Reported progress is only `early`/`middle`/`late`/`unknown` based on a bounded fraction of the move budget; no per-move traces are stored. The cohort is `first_observed`, `early_observed` (2–5 starts), or `established_observed` (6+); it is **not** a claim about the player's first-ever play, since older account history may predate this instrument.

The JSONL row contains only UTC day, bounded level, mode, rules version, objective profile, difficulty, observed cohort, optional keyed seed group, outcome, bounded assistance counts, and a coarse reported progress bucket. It does **not** include a player/attempt ID, IP, location, raw seed, board, transcript, or exact timestamp. Set `OBSERVATION_SEED_KEY` to a stable, operator-managed secret of at least 32 characters to enable a 16-hex-character HMAC seed group. Without it there is **no** seed breakdown. Treat the key and small raw slices as sensitive, keep the key outside the repository and do not publish raw JSONL. A seed group is pseudonymous, not proof of anonymity. Protect and rotate the local file according to the deployment's privacy policy.

- Default file: `var/attempt-observations.jsonl` (git-ignored); override via `ATTEMPT_OBSERVATIONS_FILE`. It is append-only, created mode `0600` where supported; writes and reads are best-effort. Back it up or rotate it as a unit: splitting starts and outcomes across files invalidates rates. The reader accepts files up to 8 MiB, then refuses the report until the file is archived/rotated; it reports malformed/skipped lines. Arrange secure rotation/retention and an aggregation job before a larger deployment. Multi-replica file storage and the current process-local economy lock are **not** production-grade shared telemetry/transactions.
- Admin token and allowed ID: `GET /api/admin/attempt-observations` for the last 30 UTC days. `?bySeed=true` adds seed group to the grouping only when keyed. Groups are suppressed below **20 server-issued starts**; the response reports `suppressedGroups` and `skippedLines` but never returns raw rows. Cache is disabled. An unclosed start is `unsettled`, not a loss. If more terminal rows than starts exist in a slice (`incompleteLog`), denominator-based rates are withheld. `verifiedWinPerStart` is a **lower bound on confirmed outcomes among starts observed**, not a human win probability; late clients, missing writes, unreported losses, active runs, timeouts and multi-device play bias it. `verifiedShareOfSettled` is not a retention metric.
- The legacy `GET /api/admin/level-tuning` and signed-in `GET /api/level-results/tuning` are labelled `legacy_client_reported_only`. A client can fabricate those reports; do not compare them to replay-verified generated wins or call them causal results.

## Safe adjustment procedure — still gated

**No generated target is auto-tuned.** Generated definitions (board, goals, move budget and rating target) are pinned on the paid spend and cannot be changed in flight. Older legacy score targets are now pinned at spend as well and returned to the web client for display. The old optional `LEVEL_TUNING_INTERVAL_HOURS` job generates review suggestions only; it **never writes** `config/level-overrides.json`. The legacy apply route is disabled unless `LEVEL_TUNING_MANUAL_ENABLED=1`. A session-authenticated admin must first inspect `GET /api/level-results/tuning`, then approve *one* proposed legacy level with its exact `expectedFrom` and `expectedUpdatedAt` values and a preregistered `reviewId` (`review-...`). Stale approvals return 409. The server audits the approval. This older route still uses self-reported data, so **do not enable it as a substitute for the experiment below**. It does not tune generated boards.

Before any difficulty change, record an operator-owned experiment plan (ID, hypothesis, objective profile and seed/level inclusion, immutable rules version, duration, exclusion rules, randomization/assignment, sample sizes/power, rollback owner). Compare a held-out control to **one** new versioned generated candidate, never mutate live paid definitions. Preregister **first-play valid-move and goal-comprehension**, perceived fairness stratified by input/access needs, verified starts/completions with unknown outcomes shown, consent-based D1/D7 return, and crash-free sessions by real device. Predefine minimum sample and stop thresholds in the plan; the current 20-start privacy threshold is **not** statistical power. Do not call a win-rate shift success if understanding, fairness, retention, or reliability declines. Monitor false replay rejections, missing logs and duplicate spends as trust guardrails. If results fail or guardrail signals are missing, stop and roll back the *new* definition version only; pinned old attempts must continue to use the old version.

**Open gates:** an [optional web D1/D7 return study](WEB_RETURN_STUDY.md) now exists but is **disabled by default** and has no real cohort evidence yet; it is not crash-free-session measurement. A separate [offline web stability kit](WEB_SESSION_STABILITY.md) can evaluate operator-supplied consented sessions, but has no real beta data or automatic crash reporting. An [offline facilitator-run first-play/fairness study kit](WEB_FIRST_PLAY_STUDY.md) is available, but no real-player baseline or threshold has been validated on physical phones or assistive tech. First-play-comprehension instrumentation, randomized assignment and a controlled rollout also remain open. Therefore **no difficulty adjustment was applied**. Complete the P0 study and real-device checks before claiming a definitive game or unlocking balancing.
